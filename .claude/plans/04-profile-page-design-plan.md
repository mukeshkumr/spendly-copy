# Implementation Plan: Profile Page Design

## Goal

Deliver Step 04 as a protected, responsive profile UI using the hardcoded sample data required by the active spec. The page should establish the account summary, recent activity, and category breakdown layout without connecting these sections to the database.

## Source of truth and current status

- `CLAUDE.md` is the repository guidance, but its route table is stale: it still labels `/profile` as a stub.
- The requested `.claude/specs/04-profile-page.md` does not exist. The matching current spec is `.claude/specs/04-profile-page-design.md`; use that as the behavioral source of truth.
- The profile route, context processor, template, page stylesheet, and conditional navbar are already present in the worktree. Implementation should verify and refine this state rather than create duplicate code.
- The requested `frontend-design` skill is available in the repository at `.claude/skills/frontend-design/SKILL.md`. Apply its Flask/Jinja/vanilla-CSS, scoped styling, whitespace, restrained fintech visual guidance while retaining Spendly's existing palette and tokens.

## Scope

### In scope

- Protect `GET /profile` using `session.get("user_id")`.
- Redirect guests to `url_for("login")`.
- Render the four spec sections with hardcoded Python data:
  - User card with initials, name, email, and member-since date.
  - Three or more summary metrics.
  - Recent expense table with date, description, category, and amount.
  - Category totals with class-based labels and/or progress indicators.
- Display the authenticated username and sign-out link in the shared navigation; retain sign-in and registration links for guests.
- Keep profile-specific presentation in a dedicated stylesheet.

### Out of scope

- Database reads or writes, schema changes, migrations, or database helpers.
- Profile editing, password changes, expense CRUD, or changes to login/logout behavior.
- New packages, JavaScript frameworks, or unnecessary client-side JavaScript.
- Replacing hardcoded prototype values with live account/expense data before the later data-wiring step.

## Implementation sequence

### 1. Confirm and preserve route behavior — `app.py`

- Keep the `/profile` route as a single-responsibility view.
- Verify the first branch checks `session.get("user_id")`; if absent, redirect to `url_for("login")`.
- For authenticated requests, pass static Python dictionaries/lists to `profile.html`; do not call `get_db()` or add SQL.
- Keep sample values internally coherent: summary totals, transaction examples, category totals, and category progress maximum should represent the same sample month.
- Keep all values escaped/rendered through Jinja's standard autoescaping.

### 2. Verify the authenticated navigation — `app.py`, `templates/base.html`, `static/css/style.css`

- Preserve the conditional navigation:
  - Authenticated: profile/name link and sign-out link.
  - Guest: sign-in and get-started links.
- Keep route targets generated by `url_for()`.
- Ensure authenticated account links are not hidden by the existing narrow-screen navigation rule.
- Treat the shared username as prototype content, consistent with the spec's no-database rule.

### 3. Verify page structure and accessibility — `templates/profile.html`

- Extend `base.html` and load the page stylesheet through the existing `head` block.
- Keep the four required sections clearly labeled with semantic headings.
- Use a semantic table with column headers for recent transactions and readable amount alignment.
- Use category CSS classes rather than inline color declarations.
- Keep all internal links generated with `url_for()`.
- Do not add inline styles or hex color literals to the template.

### 4. Refine responsive visual styling — `static/css/profile.css`

- Scope page selectors with the profile prefix to avoid leaking styles.
- Reuse established CSS variables from `static/css/style.css` for color, typography, surfaces, borders, and radii; retain the existing forest-green/gold Spendly palette rather than introducing a second palette.
- Follow the skill's restrained fintech treatment: clear hierarchy, consistent spacing, subtle borders, comfortable whitespace, and tabular alignment for currency values.
- Keep the desktop layout as a user summary, three-stat row, and transaction/category content grid.
- At tablet widths, stack the content panels; at narrow mobile widths, stack the summary cards and allow the transaction table to scroll horizontally without breaking the page.
- Avoid external icon or styling dependencies; icons are not necessary for this page's information hierarchy.

### 5. Add focused route/template tests

- Add focused pytest coverage for the profile route and navigation if the implementation work is not already covered by an existing suite.
- Verify:
  - Guest `GET /profile` redirects to login.
  - Authenticated `GET /profile` returns 200.
  - The rendered page includes user name/email, three summary metrics, at least three transaction rows, and at least three category entries.
  - Authenticated navigation shows the account/profile and sign-out links.
  - Guest navigation retains sign-in and registration links.
  - The route uses only the hardcoded presentation data and does not perform a database query.
- Use the project's existing pytest setup; do not add dependencies.

### 6. Update directly related roadmap documentation

- Update only the `/profile` row in `CLAUDE.md` to reflect Step 04's implemented status after the behavior is verified.
- Leave other route statuses unchanged; `/logout` documentation is a separate discrepancy and is not part of this feature.
- Keep the active spec's hardcoded-data/no-database constraint explicit until the later data-wiring milestone.

## Design and behavior decisions

- **Spec filename:** use `.claude/specs/04-profile-page-design.md`; do not create a duplicate spec to satisfy the alternate filename in the request.
- **Prototype identity:** the UI's profile identity remains hardcoded, even when another account is signed in. This is intentional for this UI milestone; do not imply the sample identity is sourced from the actual account.
- **No database activity:** despite the database existing, the current step deliberately presents mock data only.
- **Shared stylesheet:** global navigation changes remain in `base.html`/`style.css`; page-specific layout remains isolated in `profile.css`.
